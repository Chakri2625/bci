# Data Layer Architecture

## 1. Purpose of the Data Folder
The `data/` directory is strictly reserved for ephemeral, runtime, and persistent system data generated by SynaptiMesh. It acts as the local storage boundary, ensuring that operational data is kept cleanly separated from logic (`core/`) and structure (`config/`).

## 2. What Runtime Data is Stored Here
Currently, the system is highly memory-driven. In the near future, this folder will house:
- Output logs from the system logger.
- Serialized state dumps (crash recovery).
- Historical session telemetry.
- BCI Command history for machine learning reinforcement loops.

## 3. What Files May Be Added in Future
JSON files, SQLite databases, CSV exports of ML feature extractions, and `.log` rotation files will naturally populate this directory as the framework expands.

## 4. Difference between `config/` and `data/`
- **`config/`**: Contains static, human-readable YAML/JSON files used to initialize the application (ports, plugin toggles, environment variables). These are typically committed to Git.
- **`data/`**: Contains dynamic, machine-generated outputs. These files change constantly during execution and are heavily `.gitignore`d.

## 5. Logging Strategy
Logs will be written to `data/logs/` using a daily rotation strategy (e.g., `synaptimesh_2026-08-14.log`) to prevent disk bloating.

## 6. State Persistence Strategy
The `StateManager` currently keeps the session tree in RAM. Future upgrades will periodically dump `active_domain`, `active_app`, and `current_level` to `data/state/` to survive application restarts.

## 7. Session Persistence Strategy
Long-running BCI sessions (e.g., patient trials) will be serialized into `data/sessions/` to allow seamless resumption and historical performance tracking.

## 8. Command History Persistence
The rolling command history will eventually stream to `data/history/` to build datasets for refining the ML decoding models asynchronously.

## 9. Safety Rules
- **NEVER** commit user interaction logs, personal data, or session histories to version control.
- Ensure the root `.gitignore` correctly ignores `data/*` except for `data/.gitkeep` or `data/README.md`.

## 10. Example Future Structure
```text
data/
├── logs/     # Daily application and error logs
├── state/    # Periodic state checkpoints for crash recovery
├── sessions/ # Long-running user session metrics
├── history/  # Raw BCI command sequences for ML training
└── cache/    # Temporary files used by plugins
```

## Current Status
Currently, the simulator stores almost all state directly in memory for ultra-fast UI rendering. The `data/` folder is actively prepared and structured to support the incoming Phase 3 persistent storage and ML-debugging requirements.
